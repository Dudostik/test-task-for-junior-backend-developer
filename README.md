# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## Проверка работоспособности через Swagger UI

### 1. Открой Swagger UI

Перейдите в браузере: `http://localhost:8080/swagger/`

Должны отображаться два раздела API:

- **Tasks** — управление задачами
- **Patterns** — управление шаблонами периодичности

### 2. Проверка обычных задач (Tasks)

#### Создать задачу:

1. Разверните `POST /api/v1/tasks`
2. Нажмите **"Try it out"**
3. В поле "Request body" вставьте:

```json
{
  "title": "Проверить пациента",
  "description": "Запись к кардиологу",
  "status": "new"
}
```

4. Нажмите **"Execute"**
5. Ожидаемый результат: `201 Created` и данные задачи в ответе

#### Получить список задач:

1. Разверните `GET /api/v1/tasks`
2. Нажмите **"Try it out"** → **"Execute"**
3. Ожидаемый результат: `200 OK` с массивом задач

#### Получить задачу по ID:

1. Разверните `GET /api/v1/tasks/{id}`
2. Нажмите **"Try it out"**
3. В поле `id` введите `1`
4. Нажмите **"Execute"**
5. Ожидаемый результат: `200 OK` с данными задачи

#### Обновить задачу:

1. Разверните `PUT /api/v1/tasks/{id}`
2. Нажмите **"Try it out"**
3. В поле `id` введите `1`
4. В поле "Request body" вставьте:

```json
{
  "title": "Обновлённая задача",
  "description": "Новое описание",
  "status": "in_progress"
}
```

5. Нажмите **"Execute"**
6. Ожидаемый результат: `200 OK`

#### Удалить задачу:

1. Разверните `DELETE /api/v1/tasks/{id}`
2. Нажмите **"Try it out"**
3. В поле `id` введите `1`
4. Нажмите **"Execute"**
5. Ожидаемый результат: `204 No Content`

### 3. Проверка шаблонов периодичности (Patterns)

#### Создать daily шаблон (каждый день):

1. Разверните `POST /api/v1/patterns`
2. Нажмите **"Try it out"**
3. В поле "Request body" вставьте:

```json
{
  "name": "Ежедневный обход",
  "description": "Обход пациентов в отделении",
  "type": "daily",
  "interval_days": 1,
  "is_active": true
}
```

4. Нажмите **"Execute"**
5. Ожидаемый результат: `201 Created` с данными шаблона

#### Создать monthly шаблон (5-го числа каждого месяца):

1. Разверните `POST /api/v1/patterns`
2. Нажмите **"Try it out"**
3. Вставьте:

```json
{
  "name": "Формирование отчёта",
  "description": "Подготовить ежемесячный отчёт",
  "type": "monthly",
  "day_of_month": 5,
  "is_active": true
}
```

4. Нажмите **"Execute"**
5. Ожидаемый результат: `201 Created`

#### Создать specific шаблон (конкретные даты):

1. Разверните `POST /api/v1/patterns`
2. Нажмите **"Try it out"**
3. Вставьте:

```json
{
  "name": "Плановые операции",
  "description": "Провести плановые операции",
  "type": "specific",
  "specific_dates": ["2024-12-25T00:00:00Z", "2024-12-31T00:00:00Z"],
  "is_active": true
}
```

4. Нажмите **"Execute"**
5. Ожидаемый результат: `201 Created`

#### Создать even/odd шаблон (чётные дни):

1. Разверните `POST /api/v1/patterns`
2. Нажмите **"Try it out"**
3. Вставьте:

```json
{
  "name": "Инвентаризация",
  "description": "Проверить склады",
  "type": "even_odd",
  "even_odd_type": "even",
  "is_active": true
}
```

4. Нажмите **"Execute"**
5. Ожидаемый результат: `201 Created`

#### Получить все шаблоны:

1. Разверните `GET /api/v1/patterns`
2. Нажмите **"Try it out"** → **"Execute"**
3. Ожидаемый результат: `200 OK` с массивом шаблонов

#### Получить шаблон по ID:

1. Разверните `GET /api/v1/patterns/{id}`
2. Нажмите **"Try it out"**
3. В поле `id` введите существующий id
4. Нажмите **"Execute"**
5. Ожидаемый результат: `200 OK` с данными шаблона

#### Обновить шаблон:

1. Разверните `PUT /api/v1/patterns/{id}`
2. Нажмите **"Try it out"**
3. В поле `id` введите существующий id
4. Вставьте (пример для id 2 у меня):

```json
{
  "name": "Ежедневный обход",
  "type": "daily",
  "is_active": false
}
```

5. Нажмите **"Execute"**
6. Ожидаемый результат: `200 OK`

#### Удалить шаблон:

1. Разверните `DELETE /api/v1/patterns/{id}`
2. Нажмите **"Try it out"**
3. В поле `id` введите существующий id
4. Нажмите **"Execute"**
5. Ожидаемый результат: `204 No Content`

### 4. Проверка обработки ошибок (граничные случаи)

#### Создать daily без interval_days (должен вернуть 400):

1. Разверните `POST /api/v1/patterns`
2. Нажмите **"Try it out"**
3. Вставьте невалидный запрос:

```json
{
  "name": "Невалидный шаблон",
  "type": "daily",
  "is_active": true
}
```

4. Нажмите **"Execute"**
5. Ожидаемый результат: `400 Bad Request`

#### Создать monthly с day_of_month = 31 (должен вернуть 400):

1. Разверните `POST /api/v1/patterns`
2. Нажмите **"Try it out"**
3. Вставьте:

```json
{
  "name": "Невалидный monthly",
  "type": "monthly",
  "day_of_month": 31,
  "is_active": true
}
```

4. Нажмите **"Execute"**
5. Ожидаемый результат: `400 Bad Request`

#### Запросить несуществующий шаблон (должен вернуть 404):

1. Разверните `GET /api/v1/patterns/{id}`
2. Нажмите **"Try it out"**
3. В поле `id` введите `999`
4. Нажмите **"Execute"**
5. Ожидаемый результат: `404 Not Found`

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

Шаблоны периодичности

- `POST /api/v1/patterns` — создать шаблон
- `GET /api/v1/patterns` — список шаблонов
- `GET /api/v1/patterns/{id}` — получить шаблон
- `PUT /api/v1/patterns/{id}` — обновить шаблон
- `DELETE /api/v1/patterns/{id}` — удалить шаблон

Типы периодичности

**Ежедневные (daily)**

```json
{
  "type": "daily",
  "interval_days": 1
}
```

**Ежемесячные (monthly)**

```json
{
  "type": "monthly",
  "day_of_month": 5
}
```

**Конкретные даты (specific)**

```json
{
  "type": "specific",
  "specific_dates": ["2024-12-25T00:00:00Z", "2024-12-26T00:00:00Z"]
}
```

**Чётные/нечётные дни (even_odd)**

```json
{
  "type": "even_odd",
  "even_odd_type": "even"
}
```

## Решения

### Сценарии использования

#### Реализованные сценарии:

- Создание/редактирование/удаление шаблонов
- Временная приостановка шаблона (`is_active = false`)
- Ограничение генерации по датам (`start_date`/`end_date`)

#### Дополнение: Сценарии, которые можно было бы реализовать:

- Задачи генерируются в момент создания/обновления шаблона на ближайшие 30 дней
- Изменение даты выполненной задачи
- Сложные правила (каждый вторник и четверг)
- Уведомления
- Права доступа

### Ограничения

| Ограничение                            | Причина                                                                                                           |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Monthly только 1-30 числа              | В феврале нет 31 дня, а 30 есть не во всех месяцах. Для трекера задач такое упращение мне кажется вполне валидным |
| Максимальный период генерации 365 дней | Защита от случайного запроса на 10 лет вперёд (например, daily интервал 1 день → 3650 задач).                     |
| Все даты в UTC                         | Для единообразия.                                                                                                 |
| Нет автоматической генерации           | Для контроля создания задач.                                                                                      |
| Specific даты хранятся отдельно        | Упрощает индексирование и поиск, не нужно парсить JSON в БД.                                                      |
| Parent_task_id nullable                | Не ломает существующие задачи и позволяет строить иерархии.                                                       |

### Обоснование технических решений

#### 1. Почему отдельная таблица `task_patterns`, а не поле `recurrence_rule` в `tasks`?

- Разделение ответственности, Масштабирование, Изменяемость, Простота индексов

#### 2. Почему генерация через отдельный endpoint, а не в рантайме при создании задачи?

- Контроль, Производительность, Тестируемость

#### 3. Почему ON DELETE SET NULL?

- Сохранение истории, Аудит

### Граничные случаи

1. **Пустой список specific_dates** → ошибка валидации.
2. **Day_of_month = 31** → ошибка (неподдерживаемое значение).
3. **Interval_days = 0 или отрицательный** → ошибка.
4. **Start_date > end_date** → пустой результат генерации (не ошибка).
5. **Even_odd_type с daily/monthly** → ошибка валидации типа.
6. **Генерация на 29 февраля** → monthly правильно обрабатывает (если year високосный).
7. **Один и тот же шаблон генерирует дубликаты** → API не проверяет существование задач (ответственность клиента).
8. **Передача отрицательного ID** → 400 Bad Request.

### Что можно добавить в будущем

1. **Поддержка 31 числа** — изменить валидацию и логику monthly.
2. **Сложные правила (каждый вторник)** — добавить новый тип `weekly` с полем `weekdays`.
3. **Исключаемые даты** — таблица `pattern_excluded_dates`.
4. **Автоматическая генерация по cron** — отдельный воркер, вызывающий `/generate`.
5. **Пагинация** — добавить `limit`/`offset` в `GET /tasks`.
6. **Webhooks** — уведомлять внешние системы о создании задач.
